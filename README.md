# MFS Payments Analytics

End-to-end analytics pipeline for mobile financial services (MFS) transaction data:
Python data generation, a Power BI star-schema model, cohort retention analysis,
rules-based fraud detection, and an Excel unit-economics model.

Built as a portfolio project to work through the kind of analysis a payments or
fintech analytics team does: growth metrics, user retention, fraud signals, and
contribution margin.

## The data

**The transaction data is synthetic.** Real MFS transaction-level data is not
public, so `data.py` generates it. The macro context (bKash published fee rates)
is real and sourced.

Running `python data.py` produces ~52,000 transactions across 3,000 users and
18 months (January 2025 – June 2026), with a fixed random seed so the output is
reproducible.

The generator deliberately builds in behaviour that makes the downstream analysis
meaningful:

| Pattern | Why it matters |
|---|---|
| Payday spikes on the 1st and 25th–28th | Reflects salary cycles; makes day-of-month analysis non-trivial |
| Friday damping | Friday is the weekend in Bangladesh |
| User growth over time | Later cohorts are larger, as on a growing platform |
| Monthly churn with reactivation | Without churn, every cohort retains 100% and retention analysis is meaningless |
| Lognormal transaction amounts | Most transactions small, a few very large — spans 50 to 500,000 BDT |
| Channel-specific failure rates | USSD fails more often than the app |
| Agent concentration (Zipf-like) | A few agents handle most volume |

The amount distribution spanning four orders of magnitude is what makes the
Benford's Law test valid — a narrow range would not follow the expected
leading-digit distribution regardless of whether the data were manipulated.

The script prints six sanity checks on every run (growth trend, day-of-month
spikes, amount distribution, observed vs expected Benford distribution, failure
rates by channel, cohort sizes) so the patterns can be verified before the data
reaches Power BI.

**Requirements:** Python 3.10+, `pandas`, `numpy`.

## The model

A star schema: `transactions` as the fact table, `DateTable` as a dedicated date
dimension, joined on a date-only column derived from the transaction timestamp.

Two modelling decisions worth noting:

**A dedicated, marked date table.** Time intelligence functions such as
`DATEADD` and `TOTALYTD` require a continuous, gapless date dimension. Using the
transaction timestamps directly would silently skip days on which no transactions
occurred, producing incorrect period-over-period comparisons.

**Auto date/time disabled.** Power BI's automatic date hierarchies create a
hidden date table behind every date column in the model, which bloats the file
and conflicts with the explicit date dimension.

### Measures

| Measure | Purpose |
|---|---|
| `Total Volume` | Sum of transaction amounts (TPV) |
| `Transaction Count` | Row count |
| `Active Users` | Distinct users |
| `Avg Ticket Size` | Volume ÷ count |
| `Success Rate` | Successful transactions as a share of all |
| `Take Rate Revenue` | Fee revenue at the published cash-out rate |
| `Volume MoM %` | Month-over-month growth |
| `Volume Rolling 3M` | Three-month rolling volume |
| `Volume YTD` | Year-to-date volume |
| `Retention %` | Share of a cohort still active N months after joining |

### Cohort retention

Each user is assigned a cohort based on the month of their first transaction.
`Retention %` divides the distinct active users in a given month-since-joining by
the total size of that cohort, using `ALL()` to remove the column filter from the
denominator.

The result is displayed as a triangle: cohorts down the rows, months since
joining across the columns, conditional formatting showing the decay.

*Note on the January 2025 cohort:* it contains only 45 users, so its retention
percentages are noisier than later cohorts. This is a property of a growing
platform rather than a data problem.

*Note on April 2025 volume:* month-over-month growth reads 171.85%, against
20–30% in most other months. With only ~600 transactions that month, a small
number of transactions near the 500,000 BDT ceiling dominate the total. Once
monthly volume exceeds ~5,000 transactions the swings settle into a normal range.
This is expected behaviour for a heavy-tailed amount distribution.

## Fraud detection

50 of the 3,000 users are fraudulent, planted by the generator. Each shows a
random 2–4 traits out of five: **layering** (cash-in followed quickly by
cash-out), **structuring** (amounts just below round thresholds), **velocity**
(bursts of transactions), **odd hours**, and **agent concentration**. No
fraudster shows all five — uniform fraud would be trivially detectable and would
make the evaluation meaningless.

The labels are written to `data/fraud_labels.csv`, which is git-ignored and was
not opened until after the detection rules were finalised. Tuning thresholds
against known labels is data leakage and would make the results below
meaningless.

### Rules

| Rule | Logic |
|---|---|
| Velocity | 6 or more transactions by one user within the same clock hour |
| Structuring | Amount within 800 BDT below 10k / 25k / 50k / 100k thresholds |
| Odd hours | Transaction between 01:00 and 05:00 |

A user is flagged if **two or more** rules fire on any of their transactions.

### Results

```
Users flagged:        59 of 2,965  (2.0%)
True positives:       30 of 50 planted fraudsters
Recall:               59%
Precision:            51%
```

### Why a threshold of two signals

At three signals only 5 users got flagged. That's too few to be useful — with 50
fraudsters planted, catching 5 means missing almost everything.

There's also a structural reason three doesn't work. Each fraud user only shows 2
to 4 traits out of five, and I only wrote rules for three of the five. So a
fraudster whose traits are structuring and odd hours can trigger at most two of my
rules. They can never reach three, no matter how obvious their behaviour is.
Setting the bar at three would rule out whole groups by design.

Two signals gives 59 flagged users out of 2,965, about 2%. That's a caseload an
analyst could actually review. One signal would have been far too noisy — odd
hours alone fires on thousands of ordinary transactions, because plenty of normal
people transact at 3am.

### Why 20 fraudsters were missed

I wrote rules for velocity, structuring, and odd hours. The generator also plants
layering (cash-in followed quickly by cash-out) and agent concentration
(repeatedly using the same two or three agents). I had no rule for either.

So a fraudster whose traits were layering plus agent concentration was invisible
to my detection. Not because the rules were badly tuned, but because I wasn't
looking for what they were doing.

That part didn't surprise me once I thought about it, but it did change how I read
the result. A 59% recall doesn't mean my thresholds were slightly off — it means
two whole categories of behaviour had no detection at all. Those are different
problems with different fixes.

### What I would add next

A layering rule first. For each cash-in, check whether the same user made a
cash-out of a similar amount within about 30 minutes. Matching pairs rather than
looking at single transactions, so it needs a self-join on user and time window.

Then agent concentration. For each user, work out what share of their transactions
went through their single most-used agent. A normal customer uses whichever agent
is nearby; someone running money through a specific agent repeatedly looks
different.

I'd expect recall to go up a lot, since those two rules cover exactly the
fraudsters I'm missing now. Precision is harder to predict — agent concentration
especially could fire on ordinary people in rural areas who only have one agent
available. That's the tradeoff to watch.

These rules were **not** implemented after seeing the results. Tuning against
known labels would invalidate the precision and recall reported above.

## Unit economics

`unit_economics.xlsx` models contribution per transaction and monthly profit,
with a two-variable sensitivity table across take rate and cash-out share.

| Input | Value | Source |
|---|---|---|
| Take rate | 1.85% | [bKash published cash-out charge](https://www.bkash.com/en/products-services/cashout) — Tk 18.50 per Tk 1,000 at a standard agent |
| Average ticket size | 9,575 BDT | Derived from the transaction data |
| Cash-out share of transactions | ~15% | Derived from the transaction data |
| Agent commission | 40% of fee | **Assumption** — not publicly disclosed |
| Processing cost per transaction | 1.20 BDT | **Assumption** |
| Fraud loss rate | 0.01% of value | **Assumption** |

**A correction worth recording.** The first version of this model applied the
1.85% take rate to all transaction volume. That is wrong: bKash charges nothing
to the customer for merchant payments and a flat Tk 5 for send-money, so only
cash-out carries a percentage fee. Since cash-out is roughly 15% of transactions,
the original model overstated revenue by around six times.

A second error came from mixing bases — agent commission was initially modelled
as a percentage of transaction *value* rather than of *fee revenue*, which
produced a negative contribution margin. Every cost has to sit on the same basis
as the revenue it is netted against.

The sensitivity table exists because three of the six inputs are assumptions. It
shows monthly profit across a range of take rates and cash-out shares, so a wrong
assumption moves the answer to a different cell rather than invalidating the
analysis.

## Limitations

**Synthetic transaction data.** The patterns are designed rather than observed.
Real fraud is more varied and less separable than anything a generator plants.

**Velocity uses clock-hour buckets, not a rolling window.** A true rolling
one-hour window (counting, for each transaction, all transactions by that user in
the preceding 60 minutes) exceeded available memory on the machine used to build
this. Clock-hour bucketing is an approximation: a burst straddling an hour
boundary — five transactions at 10:58 and five at 11:02 — reads as two quiet
hours and is missed.

**Three of six unit-economics inputs are assumptions.** Agent commission,
processing cost, and fraud loss rate are not publicly disclosed. The sensitivity
table addresses the two most material ones.

**Small early cohorts.** The first few cohorts contain 45–90 users, so their
retention percentages carry more sampling noise than later ones.
